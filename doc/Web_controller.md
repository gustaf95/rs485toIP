# Web PTZ Controller

ZU-EPC7000 물리 컨트롤러(`doc/EPC7000컨트롤러.png`)를 브라우저로 옮긴 제어 패널이다.
게이트웨이가 스스로 명령의 출발점이 되어, 카메라에 따라 두 갈래로 내보낸다.

```text
브라우저 ──HTTP/Wi-Fi(STA)──> ESP32 ─┬─IP VISCA───────────> FoMaKo (IP가 설정된 슬롯)
                                     └─RS485 Pelco-D 마스터─> ED-P  (IP가 없는 슬롯)
                                          ↑ ZU-EPC7000도 같은 선에 물려 있다 (6절)
```

이 문서는 **구현된 동작**을 적는다. 코드는 다음에 나뉘어 있다.

| 파일 | 역할 |
|---|---|
| `web/control.html` | **화면 원본** — 이걸 고치면 된다. 빌드 시 `tools/embed_web.py`가 gzip PROGMEM 배열로 굽는다 ([web/README.md](../web/README.md)에 브라우저 미리보기 방법) |
| `WebControl.h/.cpp` | `/control`·`/api/*` 라우트, AP 차단 판정 (구워진 페이지를 내보내기만 한다) |
| `main.cpp` | 명령 실행(`webExecuteCommand()`), 상태 조립(`webStateJson()`), RS485 송신 큐, deadman, 버스 스니핑 |
| `config.h` | `WEB_*` 상수 (유휴 간격, deadman 타임아웃, 큐 깊이) |

명령 생성 로직을 웹 레이어에 두지 않은 이유는 9절에 있다.

## 1. 접근 경로 — STA 주소로만 제어된다

| 접속 경로 | 화면 | 제어 |
| --- | --- | --- |
| STA(평소 Wi-Fi) 주소 | ⭕ | ⭕ |
| AP(`RS485Gateway-XXXX`, 192.168.4.1) | ⭕ 모니터링만 | ❌ 차단 |

AP는 STA 연결 여부와 무관하게 항상 떠 있고 Wi-Fi 비밀번호 하나로만 막혀 있다. 설정
화면과 달리 제어 화면은 **예배 중에 누구나 폰으로 열어두게 되는 화면**이라, 카메라를
실제로 움직이는 권한을 그 문턱에 두지 않는다.

판정은 요청이 들어온 인터페이스의 로컬 주소를 AP 주소와 비교해서 한다
(`WebControl::controlAllowed()`). 페이지 자체는 AP에서도 열리고 상태 표시도 그대로
동작하되, 화면 상단에 경고가 뜨고 조작 UI 전체가 잠긴다. `POST /api/cmd`는 서버에서도
403으로 거절하므로 화면을 우회해도 통하지 않는다.

주소는 `/control` 상단(`GW 192.168.x.x`)과 설정 화면 Status에서 확인한다.

## 2. 화면

```text
┌──────────────────────────────────────────────┐
│ GW 192.168.0.50  [STA]  [CTRL ACTIVE] Config │  ← 게이트웨이 IP / 접속 경로 / 버스 활동
├──────────────────────────────────────────────┤
│ [1][2][3][4][5][6][7]                        │  ← 카메라 선택
├──────────────────────────────────────────────┤
│ PEL-D.9600   CAM:006   192.168.0.61          │
│ IRIS :AUTO   AWB:AUTO                        │  ← LCD 에뮬레이션 (5절)
│ FOCUS:MANUAL BLC:OFF   POWER:ON              │
│ updated 2s ago                               │
├────────────────────────┬─────────────────────┤
│ IRIS  [OPEN][CLOSE]    │      ╭───────╮      │
│       [AUTO][MANUAL]   │      │   ●   │      │  ← 드래그 패드 (Pan/Tilt)
│ FOCUS [NEAR][FAR]      │      ╰───────╯      │
│       [ENT ][ESC]      │   PAN 0  TILT 0     │
│       [AUTO][MANUAL]   │                     │
│       [ONE PUSH AF]    │  ┌───┬───┬───┐      │
│       [MENU(비활성)]   │  │ 1 │ 2 │ 3 │      │
│ ZOOM  [TELE][WIDE]     │  ├───┼───┼───┤      │
│       Z-SPD: Std ▾     │  │ 4 │ 5 │ 6 │      │  ← 숫자 키패드
│ AWB   [AUTO][MANUAL]   │  ├───┼───┼───┤      │
│ BLC   [ON][OFF]        │  │ 7 │ 8 │ 9 │      │
│ POWER [ON][STANDBY]    │  ├───┼───┼───┤      │
│ R GAIN [+][-]          │  │CLR│ 0 │CAM│      │
│ B GAIN [+][-]          │  └───┴───┴───┘      │
│ BRIGHT [+][-]          │  PRESET             │
│ SHUTTER[+][-]          │  [GOTO][SET][CLEAR] │
└────────────────────────┴─────────────────────┘
  web tx sent 12 / queued 0 / dropped 0
```

- **드래그 패드**: 중심에서의 변위가 곧 속도다(축당 0~63, Pelco 속도 범위 그대로).
  중앙 12%는 데드존.
- **키패드**: 숫자를 입력하고 `CAM`을 누르면 그 번호의 카메라로 전환(1~7),
  `CLR`은 입력 지움. 입력된 숫자는 PRESET 버튼 세 개가 그대로 쓴다.
- **NEAR/ENT, FAR/ESC**: 패널에서 한 키가 두 라벨을 갖는 것과 같다 — 같은 Focus
  Near/Far 명령이고, 카메라 OSD가 열려 있으면 카메라가 ENT/ESC로 해석한다.
- 화면 잠금 기능은 두지 않았다.

## 3. 키 매핑

경로에 따라 나가는 바이트가 다르다. 근거는 전부
[pelcoD_command.md 12절](pelcoD_command.md#12-실측-확인된-명령어-셋-운용-확정)에 있는
기존 변환표이고, **웹 컨트롤러는 그 표를 반대 방향으로 쓴다.**

| 웹 버튼 | IP 경로 (VISCA) | RS485 경로 (Pelco-D) |
| --- | --- | --- |
| 드래그 패드 | `01 06 01 vv ww p3 p4` | CMND2 비트(상 08/하 10/좌 04/우 02) + 속도 |
| 손 뗌 / Stop | Pan-Tilt·Zoom·Focus Stop 3종 | `FF A 00 00 00 00 CK` |
| TELE / WIDE | `01 04 07 02/03` (Z-SPD 지정 시 `2p`/`3p`) | CMND2 0x20 / 0x40 |
| NEAR / FAR | `01 04 08 03 / 02` | CMND1 bit0 / CMND2 bit7 |
| IRIS OPEN / CLOSE | `01 04 0B 02/03` | CMND1 bit1 / bit2 |
| PRESET GOTO/SET/CLEAR | `01 04 3F 02/01/00 pp` | Extended 0x07 / 0x03 / 0x05 |
| POWER ON / STANDBY | `01 04 00 02/03` | `C3 00 02/03` |
| IRIS AUTO / MANUAL | `01 04 39 00/03` | `C3 39 00/03` |
| FOCUS AUTO / MANUAL | `01 04 38 02/03` | `C3 38 02/03` |
| AWB AUTO / MANUAL | `01 04 35 00/05` | `C3 36 00/05` ← **코드가 다르다** |
| BLC ON / OFF | `01 04 33 02/03` | `C3 33 02/03` |
| ONE PUSH AF | `01 04 38 04` → 2초 뒤 `38 03` | `C3 18 01` |
| R/B GAIN, BRIGHT, SHUTTER ± | `01 04 03/04/0E/0A 02/03` | `C3 03/04/0E/0A 02/03` |

두 방언이 갈리는 자리가 정확히 두 군데다. **AWB**는 컨트롤러가 `0x36`을 쓰는데 VISCA
`CAM_WB`는 `0x35`이고, **One Push AF**는 컨트롤러가 `0x18`을 쓰는데 FoMaKo가 그 코드를
구현하지 않아 모드 설정(`38 04`)으로 우회해야 한다. 그래서 `webSetMode()`가 VISCA 코드와
버스 코드를 **따로** 받는다.

One Push AF의 되돌리기(2초 뒤 Manual)는 **IP 경로에만** 건다. ED-P는 실물 컨트롤러가
보내는 그대로 처리하고 되돌리지 않으므로, 버스 쪽에서 우리가 끼어들 이유가 없다.

## 4. 아직 안 되는 것

| 항목 | 상태 |
| --- | --- |
| **MENU 키** | **버튼은 있으나 비활성.** 이 키가 보내는 바이트를 한 번도 캡처하지 못했다 — ZU-EPC7000의 28행 커맨드 표에도 없다. 짐작으로 채우지 않는다(AWB `0x36` 전례). **캡처 방법**: 물리 패널에서 MENU를 누르고 Debug 화면의 Unhandled Commands 또는 Raw Byte Monitor를 본다. 바이트만 확인되면 한 줄로 붙는다 |
| Z-SPD 가변속 | 선택지는 있으나 기본값은 실측된 고정속(`Std`)이다. `04 07 2p`/`3p`를 FoMaKo가 받는지 미검증이라, 0~7을 고르는 건 시험용이다. RS485 Pelco-D 줌에는 속도 필드가 아예 없어 이 설정이 적용되지 않는다 |
| 절대좌표 Query | 미구현. 웹 화면에도 Pan/Tilt/Zoom 위치 표시가 없다 ([todo.md 3.1절](todo.md)) |
| Pelco-P 버스 제어 | RS485 마스터 프레임은 Pelco-D로만 만든다. Pelco-P 벤더 확장은 실측이 없다 ([todo.md 3.2절](todo.md)) |

## 5. 상태 표시 — 물어보지 않고 엿듣는다

LCD 블록의 값은 **추가 트래픽 없이** 얻는다.

| 대상 | 출처 |
| --- | --- |
| IP 카메라 | 기존 `modeCache` — `pollCameraModeInquiries()`가 1초 주기 VISCA 조회로 이미 채우고 있다 |
| RS485 카메라 | **버스 스니핑** (`sniffBusFrame()`) |

컨트롤러가 쉬지 않고 폴링하고 있고, 게이트웨이는 그 질문과 답을 **둘 다 듣는 자리**에
있다. 그래서 컨트롤러와 똑같은 방식(질문 순서)으로 짝지으면 같은 정보가 나온다.

```text
FF 03 00 D3 19 E6 D8      컨트롤러의 질문   -> busQuery[3]에 기억
FF 03 55 D7 19 41 8C      ED-P의 답        -> 3번의 AWB/IRIS/FOCUS 복원
```

`D3 04` 응답(`FF ADDR 00 D7 00 <값>`)은 **어느 항목의 답인지가 바이트에 없어서** 직전
질문과 짝지어야만 해석된다. 500ms(`WEB_BUS_QUERY_PAIR_MS`)를 넘긴 질문은 짝짓지 않는다 —
엉뚱한 응답과 맞물려 거짓 값을 표시하느니 모르는 채로 두는 게 낫다.

컨트롤러의 `C3` SET도 지나갈 때 캐시에 반영한다(낙관적). 폴링을 기다리지 않고 즉시
화면이 따라온다.

**이 프레임들은 원래 버려지고 있었다.** 응답의 CMND2(`0xD7`)는 bit0이 켜져 있어
"Unknown extended command"로 분류돼 Unhandled 로그만 채웠다. 이제 스니핑이 먼저 흡수하고
번역 경로로 넘기지 않는다 — 응답은 애초에 명령이 아니다.

### 5.1 모르는 값은 `--`로 표시한다

`modeCache`의 초기값은 전부 Auto라 그럴듯해 보이지만, 그건 컨트롤러에게 부팅 직후에도
뭔가 답해주기 위한 값이다. 웹 화면에서까지 사실인 척하면 안 되므로 항목별 관측 여부를
`known` 비트마스크로 따로 들고, 한 번도 관측 안 된 항목은 `-`로 내보낸다.

RS485 카메라 상태는 **컨트롤러가 폴링해 줘야만** 알 수 있다. 물리 컨트롤러가 꺼져 있으면
그 카메라 줄은 계속 `-`다. 이건 고장이 아니라 설계다.

## 6. RS485 마스터 — 유휴 30ms에만 끼어든다

IP 경로는 전용 소켓이라 아무와도 안 부딪히지만, RS485는 이미 ZU-EPC7000이 마스터로 쓰고
있는 2선 버스다. 게다가 게이트웨이는 **자기 송신 중에 버스를 들을 수 없다**(DE/RE가
수신부를 끈다). 충돌을 감지할 수단이 없으므로 애초에 피하는 수밖에 없다.

규칙은 하나다: **마지막 수신 바이트로부터 `WEB_TX_BUS_IDLE_MS`(30ms) 이상 조용할 때만
보낸다.** 9600bps에서 Pelco-D 한 프레임은 약 7.3ms, 프레임 내부의 바이트 간격은 1ms
남짓이라, 30ms는 프레임 중간을 유휴로 오인하지 않으면서 폴링 사이에 들어갈 만큼 짧다.

| 동작 | 값 |
| --- | --- |
| 송신 큐 깊이 | 8 프레임 |
| 유휴 대기 상한 | 500ms (`WEB_TX_MAX_WAIT_MS`). 넘기면 버리고 `Web RS485 TX Dropped` 증가 |
| 큐가 가득 찰 때 | 가장 오래된 것부터 버린다 — 방금 누른 명령이 대기열 뒤에서 밀리면 안 된다 |
| Stop | 대기 중인 프레임을 전부 버리고 맨 앞에 넣는다 — 아직 안 나간 이동 명령은 Stop 뒤에 의미가 없다 |

한 번의 `loop()`에서 한 프레임만 내보낸다. 다음 회전에서 유휴를 다시 보므로, 그 사이
컨트롤러가 말을 시작했으면 나머지는 자동으로 미뤄진다.

**조회(`D3`)는 절대 내보내지 않는다.** 5절의 짝짓기 때문이다 — 우리가 조회를 하나 끼워
넣으면 그 답을 컨트롤러가 자기 질문의 답으로 오해해 LCD에 엉뚱한 값을 띄운다. 웹에서
버스로 나가는 것은 SET(`C3`)과 이동/프리셋 명령뿐이다.

Input Protocol이 **Pelco-D 또는 Autodetect**가 아니면 RS485 경로 자체를 거절한다. 마스터
프레임을 Pelco-D로만 만들기 때문이다 — Pelco-P는 프레이밍도 주소 규칙(wire 값 = 실제 주소
− 1)도 달라서, 실측 없이 내보내면 버스의 장비가 프레임을 잃는다.

## 7. 움직임은 임대(lease)다

물리 조이스틱은 손을 놓으면 물리적으로 중앙에 돌아온다. 브라우저에는 그런 보장이 없다 —
**Wi-Fi가 끊기거나 탭이 죽으면 마지막 이동 명령이 그대로 유지된다.** VISCA
`Pan-tiltDrive`는 Stop이 올 때까지 도는 래치 명령이므로 이건 가정이 아니라 확실히
일어난다.

```text
1. 손 뗌(pointerup/cancel)      -> 즉시 Stop            (정상 경로)
2. 누르고 있는 동안 300ms마다 같은 명령 재전송            (갱신)
3. 700ms(WEB_HOLD_TIMEOUT_MS) 동안 갱신이 없으면
   게이트웨이가 스스로 Stop 생성                          (최후 방어선)
```

3번이 핵심이다. 브라우저를 신뢰하지 않는다. 이동/줌/포커스에만 걸리며(래치 명령),
계단식인 IRIS/GAIN/BRIGHT/SHUTTER에는 걸리지 않는다.

패드는 `pointerleave`를 듣지 않는다 — 원 밖으로 조금만 나가도 멈추면 조이스틱을 끝까지
미는 조작이 안 된다. 포인터 캡처로 밖에서 손을 떼도 `pointerup`이 오고, 그마저 놓치면
deadman이 받는다.

전송량은 브라우저에서 한 번(속도 단계가 바뀔 때만 전송), 게이트웨이에서 또 한 번
(`isDuplicateViscaCommand()`의 200ms 중복 억제) 조인다. 상대 조정(IRIS/GAIN/BRIGHT)은
중복 억제를 건너뛴다 — 같은 바이트의 반복이 곧 "한 칸 더"라서 억제하면 눌러도 안 움직인다.

## 8. 대상 선택 — 슬롯의 IP 유무로 갈린다

| 슬롯 상태 | 웹 제어 경로 |
| --- | --- |
| Camera IP 설정됨 | IP VISCA (`sendToCamera()`) |
| Camera IP 비어 있음 | RS485 Pelco-D 마스터 |

**설정 필드를 새로 추가하지 않았다.** `SystemConfig`에 필드를 하나라도 넣으면 구조체
크기가 바뀌어 저장된 Wi-Fi/카메라 IP가 전부 초기화된다(readme.md 10.1절). 그 대가를 치를
만큼 이 선택이 복잡하지 않다 — 어차피 IP가 있으면 IP로 보내는 게 맞고, 없으면 버스밖에
경로가 없다.

대신 **IP를 지우면 그 슬롯이 조용히 RS485 마스터 대상으로 바뀐다**는 점은 알고 있어야
한다. 화면의 LCD 블록이 현재 경로를 항상 표시한다(IP 주소 또는 `RS485 bus`).

## 9. 기존 동작과의 관계

**웹 전용 명령 생성기를 만들지 않았다.** 웹 명령도 기존 번역 경로가 쓰는
`forwardTranslatedVisca()` / `updateModeCacheFromSet()`를 그대로 탄다. 따로 만들면 중복
억제, 모드 캐시 갱신, 확인 조회 예약, One Push AF 되돌리기가 웹 경로에서만 조용히 빠진다.
`WebControl`이 HTTP와 화면만 맡고 명령 실행을 `main.cpp`에 둔 것도 같은 이유다.

| 기존 기능 | 관계 |
| --- | --- |
| **모드 캐시** | 웹에서 바꾼 값이 캐시에 반영되므로 **물리 컨트롤러 LCD도 웹 조작을 따라온다.** 두 UI가 같은 상태를 본다 |
| **Auto Power Control** | 웹 명령도 버스 활동으로 계산한다(`recordAutoPowerChatterPacket()`). 안 그러면 웹으로만 조작할 때 버스가 조용해서 조작 도중 카메라가 스탠바이로 내려간다. (현재 운용에서는 이 기능을 꺼둔다) |
| **Pelco Response Mode** | 무관하다. 그건 "컨트롤러가 우리에게 물었을 때 답할지"의 설정이고, 웹은 그 대화의 참가자가 아니다 |
| **`isOwnedSlot()`** | 그대로다. 합성 ACK/`D7` 응답 규칙은 웹 컨트롤러가 건드리지 않는다 |
| **Debug Mode** | 웹이 내보낸 버스 프레임은 `[WEB->RS485]`로, 흡수한 응답은 `[SNIFF]`로 찍힌다 |

## 10. 확인할 것

실기기에서 확인하면 좋은 순서다. 1~2번은 버스를 건드리지 않으므로 먼저 해도 안전하다.

1. **모니터링만** — `/control`을 열고 아무것도 누르지 않은 채, 물리 컨트롤러로 카메라를
   조작해 본다. LCD 블록이 따라오면 스니핑이 동작하는 것이다. 컨트롤러가 폴링하지 않는
   카메라는 `-`로 남는다.
2. **AP 차단** — AP(`192.168.4.1`)로 접속해 페이지를 열고, 경고가 뜨고 버튼이 잠기는지
   확인한다.
3. **IP 카메라 제어**(6번 FoMaKo) — 패드/줌/포커스/모드 키. 버스에 아무것도 안 나간다.
4. **Deadman** — 이동 중에 Wi-Fi를 끊거나 탭을 닫아 카메라가 700ms 안에 멈추는지 본다.
5. **RS485 제어**(1~4번 ED-P) — 여기서부터 버스에 끼어든다. `Web RS485 TX Dropped`가
   계속 올라가면 유휴 30ms를 못 잡고 있다는 뜻이므로 `WEB_TX_BUS_IDLE_MS`를 조정한다.
   조작 중 물리 컨트롤러 LCD가 깨지거나 명령이 씹히는지도 같이 본다.
6. **MENU 캡처** — 4절 참고.

## 11. 구현하지 않는 것

| 항목 | 이유 |
| --- | --- |
| 영상 미리보기 (RTSP/MJPEG) | 이 장치는 제어 신호 변환 장치다. ESP32가 영상을 중계할 성능이 없고, 스트림은 브라우저에서 직접 보는 편이 낫다 |
| 로그인/PIN | STA 접속 자체를 신뢰 경계로 본다(1절) |
| 물리 컨트롤러 잠금 | 기술적으로 불가능하다 — 컨트롤러의 송신을 막을 방법이 없다 |
| 여러 브라우저 간 조작 조정 | last-write-wins. 잠금 프로토콜은 복잡도에 비해 얻는 게 적다 |
| WebSocket | 동기식 `WebServer`로 충분한지 먼저 본다. 비동기 서버는 콜백이 별도 태스크에서 돌아 `modeCache`/`autoPower*` 같은 단일 스레드 전제 전역과 경쟁한다 |
