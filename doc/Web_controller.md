# Web PTZ Controller 구상

ZU-EPC7000 물리 컨트롤러(`doc/EPC7000컨트롤러.png`)를 웹 UI로 옮겨, 브라우저에서 카메라를
조작하는 기능에 대한 설계 구상이다. **아직 코드에 반영하지 않았다** — 무엇을 만들지,
무엇이 위험한지, 무엇을 먼저 실측해야 하는지를 정리한 문서다.

기존 문서와의 관계:

- [readme.md](readme.md) — 현재 게이트웨이(RS485 → IP 변환)의 요구사항과 구현 상태. 13절이 지금의 Web Config Server다.
- [pelcoD_command.md](pelcoD_command.md) — Pelco-D / EDIS 벤더 확장 커맨드 대응표(실측 근거 포함)
- [todo.md](todo.md) — 아직 안 풀린 프로토콜 항목. 이 구상이 의존하는 미해결 항목은 8절에 다시 모았다.

## 1. 무엇을 만들려는 것인가

핵심은 **신호의 방향이 하나 늘어난다**는 것이다.

지금 게이트웨이는 **RS485 컨트롤러의 말을 듣고 IP 카메라에 전달하는** 한 방향 장치다.
컨트롤러가 없으면 아무 일도 일어나지 않는다.

```text
[현재]
ZU-EPC7000 ──RS485(Pelco-D)──> ESP32 ──IP VISCA──> FoMaKo
                                  └─(같은 버스의 ED-P는 컨트롤러가 직접 제어, 게이트웨이는 방청객)
```

웹 컨트롤러는 **ESP32 자신이 명령의 출발점**이 되는 기능이다. 조작자가 브라우저에서
누른 것을 ESP32가 받아, 대상에 따라 두 갈래로 내보낸다.

```text
[구상]
브라우저 ──HTTP/WiFi──> ESP32 ─┬─IP VISCA──────────> FoMaKo (6번)
                               └─RS485(Pelco-D 마스터)─> ED-P (1~4번)  ← 새로 생기는 방향
                                    ↑
                       ZU-EPC7000도 같은 선에 물려 있다 (2절 핵심 난제)
```

두 갈래의 난이도가 완전히 다르다:

| 대상 | 경로 | 난이도 | 이유 |
| --- | --- | --- | --- |
| FoMaKo 등 IP 카메라 | ESP32 → IP VISCA | **쉽다** | 전용 UDP 소켓이라 아무와도 안 부딪힌다. 기존 `sendToCamera()`를 그대로 쓴다 |
| ED-P 등 RS485 카메라 | ESP32 → RS485 Pelco-D | **어렵다** | 같은 2선 버스에 물리 컨트롤러가 이미 마스터로 있다 |

**그래서 이 문서의 결론을 먼저 적으면**: IP 카메라 전용 웹 컨트롤러(Phase 1)는 위험 요소가
거의 없고 지금 구조 위에 바로 얹을 수 있다. RS485 카메라 제어(Phase 2)는 기술적으로
가능하지만 버스 중재라는 별개의 문제를 풀어야 하고, 그 전에 실측이 필요하다.

## 2. 핵심 난제 — RS485 버스에 마스터가 둘이 된다

RS485는 2선 멀티드롭이다. 이 버스에 물린 장치는 **동시에 하나만** 송신할 수 있다.
지금 구성에서 송신 권한을 가진 것은 사실상 컨트롤러 하나뿐이고, 카메라들은 자기 앞으로 온
질문에만 답한다. 게이트웨이도 [readme.md 12.2절](readme.md)의 이유로 **자기가 담당하는
슬롯의 조회에만** 답하도록 이미 조심스럽게 제한돼 있다.

웹 컨트롤러가 ED-P를 제어하려면 게이트웨이가 **묻지 않았는데 먼저 말하는** 장치가 된다.
여기서 세 가지 문제가 생긴다.

### 2.1 물리적 충돌 (드라이버 두 개가 동시에 버스를 문다)

컨트롤러는 아이들 상태에서도 `FF ADDR 00 D3 ...` 폴링을 쉬지 않고 보낸다
([readme.md 12.2절](readme.md)에 실측 기록이 있다). 그 사이에 끼어들어 보내야 하는데,
게이트웨이는 **자기 송신 중에 버스를 들을 수 없다**(`writePacket()`이 DE/RE를 올리는
동안 수신부가 꺼진다, [todo.md 4.4절](todo.md)). 즉 충돌을 감지할 방법이 없다.

**대응 설계 — 버스 유휴 감지 후 송신**:

- 마지막 수신 바이트로부터 `WEB_TX_BUS_IDLE_MS`(초안 30ms) 이상 조용할 때만 송신한다.
- 한 프레임은 7바이트 = 9600bps에서 약 7.3ms. 유휴 창 안에 들어간다.
- 송신 대기 큐를 두고, 유휴가 안 오면 `WEB_TX_MAX_WAIT_MS`(초안 500ms) 후 포기하고
  실패 카운터를 올린다 — 무한정 쌓아두면 조작자가 손을 뗀 뒤에 명령이 뒤늦게 나간다.

**먼저 실측해야 한다**: 컨트롤러 폴링 사이의 실제 유휴 간격 분포. 30ms 유휴가 초당 몇 번
오는지 모르면 이 설계가 성립하는지 알 수 없다. Raw Byte Monitor에 타임스탬프를 붙이면
바로 측정된다(8.1절).

### 2.2 응답 짝짓기 오염 (이게 더 고약하다)

EDIS `D3` 조회의 응답(`D7`)은 **어느 질문의 답인지 응답만 봐서는 구분되지 않는다** —
컨트롤러가 자기 질문 순서로 짝을 맞춘다([readme.md 12.2절](readme.md), 실측 확인됨).

그러면 게이트웨이가 버스에 `D3` 조회를 하나 던지는 순간, 그 답으로 돌아온 `D7`을
**컨트롤러가 자기 질문의 답으로 오해한다.** 컨트롤러 LCD에 엉뚱한 값이 뜨고, 조작자는
게이트웨이가 원인이라는 걸 짐작할 수 없다.

**대응 설계 — 웹에서 RS485로 나가는 것은 SET(`C3`)과 이동 명령뿐, GET(`D3`)은 절대 안 보낸다.**

| 종류 | 버스로 내보내도 되나 | 이유 |
| --- | --- | --- |
| 이동/줌/포커스 (Standard Command) | ⭕ | 응답 자체가 없다 (ACK 모드가 꺼져 있는 한) |
| `C3` SET (전원/AWB/BLC/…) | ⭕ (조건부) | **성공한 SET에는 응답이 없다.** 실패 시 `0x66` 거절 응답이 온다 — 이걸 컨트롤러가 어떻게 처리하는지는 미확인([todo.md 2.4절](todo.md)) |
| `D3` GET | ❌ **금지** | 위 짝짓기 오염 |
| Preset Set/Goto/Clear | ⭕ | 응답 없음 |

그러면 "웹 화면에 ED-P의 현재 IRIS/AWB/FOCUS 상태를 어떻게 표시하나?"라는 질문이 남는데,
답은 5절에 있다 — **물어보지 않고 엿듣는다.**

### 2.3 조작자가 둘이 된다

물리 컨트롤러 앞에 사람이 있는데 다른 사람이 웹에서 같은 카메라를 조작하면 서로 싸운다.
막을 방법은 없지만(둘 다 정당한 마스터다) **보이게는 할 수 있다**:

- 웹 화면 상단에 "물리 컨트롤러 활동 중" 표시 — 이미 있는 버스 chatter 카운터
  (`autoPowerChatterCount`, `AUTO_POWER_CHATTER_WINDOW_MS`)를 그대로 읽으면 된다.
- 반대 방향의 배려는 불가능하다. ZU-EPC7000 LCD에 "웹에서 조작 중"을 띄울 방법이 없다.

## 3. 패널 → 웹 매핑

사진의 ZU-EPC7000 패널을 항목별로 옮긴 표다. "IP 경로"는 FoMaKo로 나갈 VISCA,
"RS485 경로"는 ED-P로 나갈 Pelco-D 바이트다. 근거는 대부분
[pelcoD_command.md 12절](pelcoD_command.md#12-실측-확인된-명령어-셋-운용-확정)에 이미 정리돼 있다 —
**웹 컨트롤러는 지금 있는 변환표를 반대 방향으로 쓰는 일**이라 새 프로토콜 해독이 거의 없다.

### 3.1 이동 계열

| 패널 | 웹 UI | IP 경로 (VISCA) | RS485 경로 (Pelco-D) |
| --- | --- | --- | --- |
| 3축 조이스틱 (Pan/Tilt) | 터치/마우스 드래그 패드. 중심에서의 변위 → 속도 | `01 06 01 vv ww p3 p4` | `FF A 00 CMND2 spd spd CK` |
| 조이스틱 비틀기 (Zoom) | 슬라이더 또는 +/− 버튼 | `01 04 07 02/03` (또는 가변속 `2p`/`3p`) | CMND2 bit5/bit6 |
| TELE / WIDE | 버튼 (누르고 있는 동안) | 위와 동일 | 위와 동일 |
| NEAR / FAR | 버튼 (누르고 있는 동안) | `01 04 08 03/02` | CMND1 bit0 / CMND2 bit7 |
| IRIS OPEN / CLOSE | 버튼 (탭마다 한 칸) | `01 04 0B 02/03` | CMND1 bit1 / bit2 |
| (손 뗌) | 자동 | Stop 3종 (P/T, Zoom, Focus) | `FF A 00 00 00 00 CK` |

Stop 처리는 이 기능 전체에서 **가장 중요한 안전 장치**다 — 6절에서 따로 다룬다.

### 3.2 모드 계열 (EDIS `C3` SET에 대응)

| 패널 키 | IP 경로 (VISCA) | RS485 경로 (`C3 pp qq`) | 비고 |
| --- | --- | --- | --- |
| POWER On / Standby | `01 04 00 02/03` | `C3 00 02` / `C3 00 03` | Auto Power Control과 충돌 주의 (7.2절) |
| IRIS AUTO / MANUAL | `01 04 39 00/03` | `C3 39 00` / `C3 39 03` | 실제로는 AE 모드 |
| FOCUS AUTO / MANUAL | `01 04 38 02/03` | `C3 38 02` / `C3 38 03` | |
| AWB AUTO / MANUAL | `01 04 35 00/05` | `C3 36 00` / `C3 36 05` | **pp가 VISCA와 다르다** (`36` ≠ `35`) |
| BACK LIGHT | `01 04 33 02/03` | `C3 33 02` / `C3 33 03` | 패널은 토글이지만 On/Off를 명시적으로 보낸다 |
| ONE PUSH AF | `01 04 38 04` → 2초 뒤 `38 03` | `C3 18 01` | IP 경로는 되돌리기까지 게이트웨이 몫 |
| R GAIN ▲▼ / B GAIN ▲▼ | `01 04 03 02/03`, `01 04 04 02/03` | `C3 03 02/03`, `C3 04 02/03` | 상대 조정 — 중복 억제 제외 대상 |
| BRIGHT ▲▼ | `01 04 0E 02/03` | `C3 0E 02/03` | 동작 조건이 어긋나는 미해결 항목([todo.md 2.5절](todo.md)) |

### 3.3 키패드 / 프리셋

| 패널 | 웹 UI |
| --- | --- |
| 숫자 0~9 + PRESET | 번호 입력칸 + [Goto] [Set] [Clear] 버튼 3개 |
| 숫자 + CAM | 카메라 선택 탭 (CAM1~7). 순수 UI 상태, 버스 트래픽 없음 |
| CLR | 입력칸 지우기. 트래픽 없음 |
| LOCK MODE | 웹 화면 잠금 토글. 트래픽 없음 — 실수 방지용 |

프리셋 명령은 IP `01 04 3F 01/02/00 pp`, RS485 Extended `00 03/05/07`로 이미 양쪽 다
구현돼 있다(`translatePelcoAndForward()`).

### 3.4 옮기지 않는 것 / 미확인

| 패널 | 판단 |
| --- | --- |
| MENU | **미확인.** 카메라 OSD 메뉴 진입인데, FoMaKo VISCA 쪽 명령도 ED-P Pelco-D 쪽 명령도 실측된 적이 없다. Phase 3 이후로 미룬다 |
| ENT / ESC (NEAR·FAR 겸용) | MENU와 한 벌이라 같이 미룬다 |
| PEL-D.9600 표시 | 웹에서는 상태 표시로만 (게이트웨이의 Input Protocol / Baudrate를 그대로 보여준다) |
| Z-SPD:[03] | 줌 속도 단계. IP 경로는 VISCA 가변속(`04 07 2p`/`3p`)으로 실현 가능하지만 **현재 게이트웨이는 고정속(`02`/`03`)만 쓴다.** RS485 Pelco-D 줌에는 속도 필드가 아예 없다 |
| TX/RX/MODE/RS-232C LED | 웹 상태 표시로 대체 (카운터 페이지가 이미 같은 정보를 준다) |

## 4. 대상 선택 모델 — 슬롯에 "제어 경로"를 추가한다

지금 카메라 슬롯의 규칙은 단순하다: **IP가 있으면 게이트웨이 담당, 없으면 남의 것**
(`isConfigured()` / `isOwnedSlot()`). 이 규칙이 [readme.md 12.2절](readme.md)의 버스 충돌
방지 전체를 떠받치고 있다.

웹 컨트롤러는 여기에 "IP는 없지만 웹에서 RS485로 제어하고 싶은 슬롯"이라는 제3의 상태를
만든다. IP 유무로 암시하지 말고 **명시적인 필드를 새로 두는 것**이 맞다 — 암시로 처리하면
IP를 지우는 순간 그 슬롯이 조용히 RS485 마스터 대상으로 승격되는, 눈에 안 보이는 사고가 난다.

```cpp
// CameraSlot에 추가 (구상)
enum class WebControlPath : uint8_t {
  NONE   = 0,  // 웹 컨트롤러에 노출하지 않음 (기본값)
  IP     = 1,  // 슬롯의 IP/Port/Protocol로 VISCA 전송 — IP가 설정돼 있어야 함
  RS485  = 2,  // RS485 버스로 Pelco-D 마스터 프레임 전송 — 2절의 위험을 감수함
};
```

| 필드 | 기본값 | 비고 |
| --- | --- | --- |
| `webControlPath` | `NONE` | 슬롯별. 켜야만 웹 화면에 그 카메라가 나타난다 |
| `webControlEnabled` (전역) | `false` | 웹 컨트롤러 기능 자체의 마스터 스위치 |
| `webRs485MasterEnabled` (전역) | `false` | RS485 경로만 따로 끄는 2단 안전장치 |

**설정 초기화 경고**: `SystemConfig`에 필드를 추가하면 구조체 크기가 바뀌어 `Storage::load()`가
실패하고 전부 기본값으로 돌아간다 — Wi-Fi와 카메라 IP를 다시 입력해야 한다
([todo.md 4.2절](todo.md)). `kConfigVersion`을 올리고 이 사실을 릴리스 노트에 함께 적는다.

## 5. 상태 표시 — 물어보지 않고 엿듣는다

패널 LCD는 4줄이다:

```text
PEL-D.9600  .CAM:001
IRIS :AUTO  .AWB:AUTO
FOCUS:AUTO
Z-SPD:[03]
```

웹에서 이 값을 보여주려면 카메라의 현재 모드를 알아야 하는데, 대상에 따라 출처가 다르다.

| 대상 | 상태 출처 | 추가 트래픽 |
| --- | --- | --- |
| IP 카메라 (FoMaKo) | 기존 `modeCache[]` — `pollCameraModeInquiries()`가 이미 1초 주기로 채우고 있다 | 없음 (이미 돈다) |
| RS485 카메라 (ED-P) | **버스 스니핑** (아래) | **없음** |

### 5.1 버스 스니핑으로 ED-P 상태를 공짜로 얻는다

2.2절 때문에 게이트웨이는 ED-P에게 직접 물어볼 수 없다. 그런데 **물어볼 필요가 없다** —
컨트롤러가 쉬지 않고 폴링하고 있고, 게이트웨이는 그 질문과 답을 **둘 다 듣고 있다.**

```text
버스에서 게이트웨이가 관측하는 것:
  FF 03 00 D3 19 E6 D8      ← 컨트롤러의 질문 (3번 카메라의 모드 상태)
  FF 03 55 D7 19 41 8C      ← ED-P의 답
      └ 이 둘을 순서로 짝지으면 3번의 IRIS/AWB/FOCUS가 그대로 나온다
```

컨트롤러가 응답을 짝짓는 방식과 정확히 같은 방식(질문 순서)으로 게이트웨이도 짝지을 수
있다. **양쪽을 다 듣는 위치라 오히려 컨트롤러보다 유리하다.**

응답 프레임 디코딩 규격은 이미 복원돼 있다
([todo.md 부록](todo.md), `sendEdisModeStatus()`가 만드는 것과 같은 포맷을 반대로 읽으면 된다):

```text
FF ADDR R1 D7 19 D2 CK       R1 = 0x50 | (WB 모드), D2 bit6 = Iris Manual, bit0 = Focus Manual
FF ADDR 00 D7 00 val CK      단일 항목 — 직전 D3 04 <item> 질문과 짝지어야 의미가 생긴다
```

**현재 코드에서 이 프레임들이 어떻게 처리되는지 확인함**: `D7` 응답은 CMND2 bit0이 1이라
"Unknown extended command"로 분류되어 조용히 버려진다(`translatePelcoAndForward()`).
즉 지금은 무해하게 무시되고 있고, 이 구상은 **버리기 전에 한 번 읽는 것**을 추가하는 일이다.
카메라 슬롯 밖 주소(8 이상)의 프레임도 스니핑 대상에 포함할지는 별도 판단이 필요하다
([todo.md 3.3절](todo.md)의 슬롯 1~7 제한과 얽힌다).

### 5.2 세 종류의 상태를 구분해서 보여준다

| 표시 | 의미 |
| --- | --- |
| `AUTO` / `MANUAL` | 확인된 값 (IP는 조회 응답, RS485는 스니핑) |
| `AUTO?` (흐리게) | 웹에서 방금 바꿨지만 아직 확인 안 된 낙관적 값 |
| `--` | 아직 한 번도 관측 못 함 (부팅 직후, 컨트롤러가 그 카메라를 폴링 안 함) |

세 번째가 중요하다. RS485 카메라 상태는 **컨트롤러가 폴링해 줘야만** 알 수 있으므로,
물리 컨트롤러가 꺼져 있으면 웹 화면에 영원히 `--`가 뜬다. 거짓 값을 그럴듯하게 채우는
것보다 모른다고 말하는 쪽이 낫다 — 이건 게이트웨이가 `D3 16` 조회에 침묵하는 것과 같은
원칙이다([todo.md 2.1절](todo.md)).

## 6. 조작 모델 — Stop을 잃어버리지 않는 설계

물리 조이스틱은 손을 놓으면 물리적으로 중심에 돌아오고 컨트롤러가 Stop을 보낸다.
브라우저에는 그런 보장이 없다 — **Wi-Fi가 끊기거나, 브라우저 탭이 죽거나, 사람이 휴대폰을
주머니에 넣으면 카메라는 마지막 이동 명령 그대로 계속 돈다.** VISCA `Pan-tiltDrive`는
Stop이 올 때까지 유지되는 래치 명령이라([readme.md 12.2절](readme.md)) 이건 가정이 아니라 확실히 일어난다.

### 6.1 3중 안전장치

```text
1. pointerup / pointercancel / blur  →  즉시 Stop 전송      (정상 경로)
2. 누르고 있는 동안 300ms마다 keepalive  →  끊기면 서버가 안다   (연결 감시)
3. 서버 워치독: 마지막 keepalive로부터 WEB_DEADMAN_MS(초안 700ms)
   경과하면 게이트웨이가 스스로 Stop 생성                      (최후 방어선)
```

3번이 핵심이다. 브라우저를 신뢰하지 않는다 — **움직임은 명시적으로 갱신되는 동안만
유지되는 임대(lease)** 로 본다. 이 모델은 지금 코드의 Stop 우선 처리 원칙
([readme.md 9절](readme.md))과 방향이 같다.

### 6.2 전송량 조절

물리 컨트롤러는 조이스틱 변위가 바뀔 때마다 새 프레임을 보내고, 램프 한 번에 7~10개의
패킷이 나간다([todo.md 1.2절](todo.md) 실측). 웹도 같은 모델을 쓰되 브라우저 쪽에서 한 번 더 조인다:

- 속도 단계가 바뀔 때만 전송 (변위를 0x00~0x3F로 양자화 후 비교)
- 최대 전송률 10Hz로 제한
- 기존 `isDuplicateViscaCommand()`(200ms 중복 억제)가 그 뒤에서 한 번 더 걸러준다

**상대 조정(R/B Gain, BRIGHT, IRIS Open/Close)은 중복 억제를 건너뛰어야 한다** — 반복이
곧 "한 칸 더"라서 억제하면 눌러도 안 움직이는 것처럼 보인다. 이미 `forwardTranslatedVisca()`에
`isRelativeStep` 인자가 있으므로 웹 경로도 같은 구분을 쓰면 된다.

## 7. 기존 기능과의 상호작용

새 기능이 지금 잘 돌아가는 것을 망가뜨리지 않아야 한다. 얽히는 지점을 전부 나열한다.

### 7.1 `isOwnedSlot()` / 합성 ACK

웹 컨트롤러는 이 판정을 **건드리지 않는다.** RS485로 응답을 지어낼지 말지는 여전히
"컨트롤러가 우리에게 물었는가"의 문제고, 웹은 그 대화의 참가자가 아니다.

### 7.2 Auto Power Control (충돌 있음, 해결 필요)

`updateAutoPowerFromChatter()`는 **RS485 버스의 유효 패킷 수**로 컨트롤러 활동을 판단해
카메라 전원을 켜고 끈다. 그런데 웹으로만 조작하면 버스는 조용하다 — **조작 중에 카메라가
스탠바이로 내려간다.**

**대응**: 웹 명령도 활동으로 계산한다. `recordAutoPowerChatterPacket()`을 웹 명령 경로에서도
호출하면 되고, 함수 이름은 "chatter"보다 "activity"에 가까워지므로 개명을 검토한다.

### 7.3 One Push AF 되돌리기

IP 경로의 One Push AF는 2초 뒤 Manual로 되돌리는 예약이 걸린다(`pollOnePushAfRestore()`).
웹에서 눌러도 같은 처리가 필요하다 — 웹 명령이 `handleEdisVendorCommand()`를 우회해 직접
VISCA를 만들면 이 예약이 빠진다.

**설계 원칙**: 웹 명령은 "웹 전용 VISCA 생성기"를 새로 만들지 말고, **기존 번역 함수들이
쓰는 것과 같은 내부 진입점**을 공유해야 한다. 안 그러면 One Push AF 되돌리기, 모드 캐시 갱신,
확인 조회 예약, 중복 억제가 전부 웹 경로에서만 빠진 채 조용히 다르게 동작하게 된다 —
Serial 메뉴와 Web Config Server가 `GatewayActions`/`Rs485PinValidation`을 공유하는 것과
같은 이유다([readme.md 13.4절](readme.md)).

### 7.4 모드 캐시

웹에서 모드를 바꾸면 `updateModeCacheFromSet()`을 똑같이 태워야 한다. 그래야 **물리
컨트롤러 LCD도 웹에서 바꾼 값을 따라온다** — 이게 되면 두 UI가 같은 상태를 본다는
꽤 좋은 성질이 공짜로 생긴다.

### 7.5 진단 정보는 웹 화면 안에 있어야 한다

웹 컨트롤러를 쓰는 상황은 대개 조작자가 USB 콘솔 앞에 없는 상황이다 — 명령이 안 먹을 때
Serial을 볼 수 없다. 마지막으로 내보낸 프레임, (Phase 3이라면) 유휴 대기 실패 횟수 같은
진단 정보를 제어 화면 자체에 노출해야 한다.

## 8. 전송 계층과 UI

### 8.1 HTTP 폴링으로 시작하고, 필요하면 WebSocket으로 간다

현재 `WebConfigServer`는 arduino-esp32 내장 동기식 `WebServer`를 쓴다(`lib_deps` 없음).
제어 UI는 설정 화면보다 지연에 민감해서 WebSocket이 자연스러워 보이지만, **처음부터
가지 않기를 권한다**:

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **동기 `WebServer` + 짧은 POST** (권장 시작점) | 의존성 0, 기존 코드와 동일 구조, 상태 공유가 단순 | 요청마다 TCP 오버헤드. `loop()`를 잠깐 붙잡음 |
| `ESPAsyncWebServer` + WebSocket | 지연 낮음, 상태 push 가능 | `lib_deps` 2개 추가, RAM 증가, **콜백이 별도 태스크에서 돌아 `loop()`와 공유 상태 경쟁** |

동기 방식의 `loop()` 블로킹은 이미 대응돼 있다 — RS485 수신 링버퍼가 1024바이트라 9600bps
기준 약 1초의 정체를 견딘다([readme.md 3.1절](readme.md)). 요청 하나는 그보다 훨씬 짧다.

WebSocket의 태스크 경쟁이 특히 위험하다. 지금 `modeCache`, `autoPower*`, `lastSent*`는 전부
단일 스레드(`loop()`)를 전제로 짜인 전역이다. 비동기 콜백에서 건드리면 락이 필요해진다.

**실측으로 판단한다**: Phase 1을 동기 방식으로 만들어 조이스틱 왕복 지연을 재본다. 체감이
나쁘면 그때 옮긴다.

### 8.2 페이지 구성

```text
GET  /control              제어 패널 (HTML+JS, PROGMEM 정적 문자열 + server.send_P)
POST /api/cmd              {cam, action, p1, p2}  → 명령 하나
POST /api/move             {cam, pan, tilt}       → 조이스틱 (keepalive 겸용)
POST /api/stop             {cam}                  → 즉시 정지
GET  /api/state?cam=N      모드/전원/연결 상태 JSON (1초 폴링)
```

HTML은 지금처럼 `String` 이어붙이기로 만들면 안 된다 — 제어 패널은 JS/CSS가 들어가
설정 페이지보다 훨씬 크다. `R"HTML(...)HTML"` raw 문자열 리터럴을 PROGMEM에 두고
`send_P()`로 내보내 힙 단편화를 피한다.

### 8.3 화면 시안

패널을 그대로 베끼기보다, 물리 패널의 **배치 논리**(상태는 위, 이동은 오른손, 모드는
왼손·윗줄)를 유지하면서 화면 크기에 적응시킨다. 세로 화면(휴대폰)에서는 한 줄로 접힌다.

```text
┌──────────────────────────────────────────────┐
│ ● 물리 컨트롤러 활동 중        [CAM1][2][3]▣6│  ← 상태바 + 카메라 선택
├──────────────────────────────────────────────┤
│ CAM:006   PEL-D.9600   IP 192.168.0.61       │
│ IRIS :AUTO    AWB:AUTO    FOCUS:MANUAL       │  ← LCD 에뮬레이션 (5절)
├────────────────────────┬─────────────────────┤
│  IRIS  [OPEN] [CLOSE]  │                     │
│  FOCUS [NEAR] [ FAR ]  │        ╭─────╮      │
│  ZOOM  [TELE] [WIDE]   │        │  ●  │      │  ← 드래그 패드
│                        │        ╰─────╯      │
│  ── 모드 ──            │      Z-SPD ▁▃▅▇     │
│  IRIS  (AUTO)(MANUAL)  │                     │
```

## 9. 보안

지금 웹 UI에는 인증이 없다 — "신뢰된 LAN/AP 전제"이고 AP 접속 비밀번호가 유일한 방어선이다
([readme.md 13.1절](readme.md)).

**제어 기능은 설정 기능보다 노출 위험이 크다.** 설정을 잘못 건드리면 나중에 고치면 되지만,
예배 중에 카메라가 엉뚱한 데를 보면 그 순간이 지나간다. 그리고 설정 페이지는 아무도 안 볼 때
쓰지만 제어 페이지는 **누구나 폰으로 열어두게 되는** 페이지다.

| 방안 | 평가 |
| --- | --- |
| 전역 활성 스위치 (기본 off) | **필수.** 안 쓰는 설치에서는 존재하지 않는 기능이 된다 |
| 4~6자리 PIN + 쿠키 세션 | **권장.** 구현 부담이 작고 실수 접근을 막는다 |
| HTTP Basic Auth | 대안. `WebServer`에 내장(`authenticate()`)이라 더 싸지만 UX가 나쁘다 |
| STA(사내망) 쪽에서는 제어 비활성, AP 접속자만 허용 | 검토할 만하다. 물리적 근접성이 곧 권한이 된다 |
| HTTPS | **하지 않는다.** ESP32에서 TLS 서버는 비용이 크고 자체 서명 인증서는 경고를 부른다 |

## 10. 단계별 계획

### Phase 1 — IP 카메라 전용 제어 (위험 없음)

FoMaKo(6번)만 대상. RS485 버스는 **전혀 건드리지 않는다.**

- `/control` 페이지, `/api/*` 엔드포인트
- 이동/줌/포커스/아이리스 + Stop 3중 안전장치(6절)
- 모드 키(3.2절) — 기존 `modeCache` / 확인 조회 재사용
- 상태 표시는 `modeCache`에서 바로
- 전역 활성 스위치 + PIN

이 단계만으로 "예배 중 폰으로 IP 카메라 조작"이라는 실사용이 성립한다. **버스에 아무것도
내보내지 않으므로 지금 잘 돌아가는 것이 깨질 위험이 없다.**

### Phase 2 — 버스 스니핑으로 상태 표시 (읽기 전용)

- ED-P `D7` 응답 디코딩 + 질문/응답 짝짓기(5.1절)
- 웹 화면에 RS485 카메라 상태를 표시 — **아직 조작은 못 한다**
- 이 단계도 송신이 없어 위험이 없고, 동시에 Phase 3의 상태 표시 기반이 미리 완성된다

### Phase 3 — RS485 마스터 (위험 구간)

- 유휴 감지 송신 큐(2.1절) + `webRs485MasterEnabled` 2단 스위치
- SET/이동만, GET 금지(2.2절)
- 충돌·대기 실패 카운터를 Counters 페이지에 추가
- **Phase 3 착수 전에 8.1절 유휴 간격 실측이 선행돼야 한다**

### Phase 4 — 나머지

- MENU/OSD (3.4절, 프로토콜 실측부터)
- 줌 가변속(Z-SPD)
- 프리셋 이름 붙이기 (NVS에 라벨 저장 — "강대상", "전경" 등)

## 13. 정리 — 이 구상에 대한 판단

**할 만한가**: Phase 1은 확실히 그렇다. 필요한 조각(라우팅, VISCA 전송, 모드 캐시,
웹 서버 골격)이 전부 이미 있고, 실제로 새로 쓰는 것은 UI와 안전한 Stop 처리뿐이다.
버스를 건드리지 않으므로 지금 동작하는 것을 위태롭게 하지 않는다.

**RS485 카메라 제어(Phase 3)는 성격이 다른 결정이다.** 기술적으로는 유휴 감지 송신으로
풀 수 있지만, "잘 돌아가는 버스에 두 번째 마스터를 넣는다"는 것 자체가 되돌리기 어려운
복잡도다. 그래서 11.1 실측 전에는 착수를 권하지 않고, 스위치도 2단으로 두자고 제안한다.

**가장 좋은 성질은 Phase 2에 있다** — ED-P 상태를 엿듣기만 해서 얻는 부분이다. 트래픽도
위험도 0인데 웹 화면이 물리 컨트롤러 LCD와 같은 것을 보게 된다. 게이트웨이가 버스의 양쪽
말을 다 듣는 위치에 있다는, 이 프로젝트만의 이점을 쓰는 곳이다.
