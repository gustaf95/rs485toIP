# 외부 프로그램용 제어 인터페이스 (CLI / API)

브라우저의 제어 패널(`/control`) 말고, **다른 프로그램이나 스크립트가** 카메라를 움직이는
경로다.

> **결정: 웹(HTTP) 기반으로 간다.** 제어 패널이 쓰는 `POST /api/cmd` / `GET /api/state`를
> 그대로 공식 인터페이스로 쓰고, PC 쪽에 얇은 래퍼 [`tools/ptz.py`](../tools/ptz.py)를 둔다.
> **펌웨어는 건드리지 않았다** — 지금 현장에 올라가 있는 장비에서 그대로 동작한다.

용례로 상정한 것:

- 예배 시작 시 "모든 카메라 프리셋 1로" 같은 **한 줄 스크립트**
- 조명·음향 콘솔이나 Companion / Node-RED 같은 **쇼 컨트롤 도구**의 버튼
- 별도의 웹 페이지(예: 교회 내부 페이지)에서 **fetch 한 방**
- 조이스틱이나 게임패드를 붙인 **작은 프로그램의 연속 이동**

---

## 1. 결정과 그 이유

| | 판정 | |
| --- | --- | --- |
| **HTTP API + `tools/ptz.py`** | **채택 (구현됨)** | 펌웨어 변경 0. 어휘가 제어 패널과 물리적으로 같다. 오류 사유가 문장으로 돌아온다. 셸·파이썬·Node·브라우저·Node-RED에서 추가 코드 없이 붙는다 |
| 텍스트 한 줄 프로토콜 (UDP/TCP) | 보류 | HTTP가 느리다고 느껴질 때만. 조건은 6절 |
| Pelco-D를 UDP로 그대로 수신 | 보류 (호환용) | Pelco-D밖에 못 뱉는 기성 도구를 붙여야 할 때만. 5절 |
| **VISCA over IP 수신** | **폐기** | RS485 카메라가 VISCA를 못 알아듣고, 게이트웨이에 VISCA→Pelco-D 번역이 없다. 7절 |

**전제 하나**: 이 게이트웨이는 **표준 Pelco-D 호환 장비가 아니다.** 지원 대상은 이 버스에
실제로 물려 있는 ED-P와, 이 프로젝트가 실측해서 알아낸 그 방언
(`doc/pelcoD_command.md`)뿐이다. 일반 Pelco-D 도구와의 호환은 목표가 아니다 — 그래서
아래 검토에서도 "표준에 없다"는 이유로 무언가를 배제하지 않는다.

## 2. 어떤 봉투를 쓰든 실행은 한 함수를 지난다

이 장치의 명령 실행은 전부 `main.cpp`의 **함수 하나**를 지난다.

```c
bool webExecuteCommand(uint8_t cam, const String& action, int p1, int p2, String* err);
```

여기서 카메라 슬롯에 IP가 있으면 IP VISCA로, 없으면 RS485 Pelco-D 마스터로 갈라진다.
중복 억제, 모드 캐시 갱신, One Push AF 되돌리기, Auto Power 활동 기록, deadman 예약이
전부 이 함수 안쪽에 붙어 있다 (`doc/Web_controller.md` 9절).

**그래서 새 인터페이스를 낸다는 것은 "새 명령 체계를 설계한다"가 아니라 "이 함수의 인자
네 개를 어떤 봉투에 담아 옮길 것인가"를 정하는 일이다.** 봉투가 무엇이든 어휘는 9절의
표 하나로 고정한다. 전송 방식마다 어휘를 따로 만들면, 나중에 기능을 하나 추가할 때 세
군데를 고쳐야 하고 한 군데를 빠뜨린다.

HTTP를 고른 이유의 절반이 이것이다 — `/api/cmd`는 이 함수를 감싼 **가장 얇은 봉투**이고,
제어 패널이 이미 그걸 쓰고 있어서 두 UI가 어긋날 수가 없다.

## 3. HTTP API 규격

### 3.1 명령

```sh
curl -s -X POST http://192.168.0.50/api/cmd \
     -d cam=6 -d action=preset_goto -d p1=3
```

| | |
| --- | --- |
| 메서드 | `POST /api/cmd` |
| 본문 | `application/x-www-form-urlencoded` — `cam`, `action`, `p1`, `p2` |
| 성공 | `200` `{"ok":true}` |
| 실패 | `200` `{"ok":false,"err":"unknown action"}` ← **HTTP 상태는 200이다** |
| 차단 | `403` `{"ok":false,"err":"control is blocked on the AP - use the STA address"}` |

실패가 200으로 오는 것은 화면이 오류 문구를 그대로 띄우려고 그렇게 둔 것이다. 스크립트를
쓸 때는 **HTTP 상태가 아니라 `ok` 필드를 봐야 한다.** `tools/ptz.py`가 그걸 종료 코드로
바꿔준다.

### 3.2 상태

```sh
curl -s http://192.168.0.50/api/state
```

`GET /api/state`가 게이트웨이 IP, 입력 프로토콜/보드레이트, 물리 컨트롤러의 버스 활동
여부, 카메라 7개의 경로(`ip`/`rs485`)와 관측된 모드(POWER/IRIS/AWB/FOCUS/BLC), 그 값이
몇 초 전 것인지(`age`)를 JSON으로 준다. 스키마는 `webStateJson()`이 유일한 출처다.

`age`가 `-1`이면 **아직 한 번도 관측되지 않은 값**이다 — RS485 카메라의 상태는 물리
컨트롤러가 폴링해 줘야만 알 수 있어서, 컨트롤러가 꺼져 있으면 영영 `-1`로 남는다.
스크립트가 "지금 AWB가 뭐지"를 물어서 분기하는 로직은 **RS485 카메라에서는 신뢰할 수
없다.** IP 카메라는 게이트웨이가 직접 조회하므로 다르다.

### 3.3 한계

- **HTTP 왕복이 붙는다.** ESP32의 동기식 `WebServer`는 `loop()` 회전마다 요청 하나를
  처리하므로, 초당 수십 번 두드리는 조이스틱 용도로는 여유가 없다. 프리셋·모드 전환처럼
  **사람이 누르는 속도**에는 전혀 문제가 없다.
- 연속 이동은 **호출자가 반복해서 보내야 한다** (8.1절 deadman). `ptz.py --for`가 대신 한다.

## 4. `tools/ptz.py` — CLI (구현됨)

게이트웨이에는 아무것도 넣지 않고 **PC 쪽에 한 파일**만 둔다. 표준 라이브러리만 쓰므로
라즈베리파이든 윈도우 콘솔 PC든 복사 한 번이면 되고, curl도 필요 없다.

```sh
export PTZ_GW=192.168.0.50        # Windows: set PTZ_GW=192.168.0.50

ptz.py 6 preset goto 3
ptz.py 6 move 40 0 --for 2        # 2초 동안 오른쪽으로 (0.3초마다 갱신 후 정지)
ptz.py 6 zoom in 3 --for 1.5
ptz.py 6 awb auto
ptz.py 6 bright up --repeat 3     # 세 칸
ptz.py all power on
ptz.py state
ptz.py state --json | jq .cams[5].awb
ptz.py help
```

`ptz.py state` 출력:

```text
GW 192.168.0.50   PEL-D.9600   BUS IDLE
CAM  PATH             POWER  IRIS    AWB     FOCUS   BLC   AGE
1    RS485 bus        ON     AUTO    AUTO    MANUAL  OFF   3s
6    192.168.0.61     ON     AUTO    AUTO    AUTO    OFF   1s
web tx sent 12 / queued 0 / dropped 0
```

### 4.1 설계 규칙과 이유

| 규칙 | 이유 |
| --- | --- |
| 주소는 `PTZ_GW` 또는 `--gw` | 매번 IP를 치지 않게. 주소는 고정해 두는 것이 사실상 전제 조건이다(8.4절) |
| **종료 코드** 0 성공 / 1 게이트웨이가 거절 / 2 통신 실패·사용법 오류 | `ptz.py ... && echo ok` 가 되게. `ok:false`를 200으로 받는 문제(3.1)를 여기서 흡수한다 |
| **0/1 대신 낱말** (`auto`/`manual`, `on`/`off`, `in`/`out`, `near`/`far`) | 9절 표를 보면 `ae 1`은 MANUAL인데 `power 1`은 ON이다. 물리 컨트롤러 키 배치를 옮긴 결과라 게이트웨이 쪽 숫자는 못 바꾸므로, 바깥으로 나가는 이름만 사람 말로 둔다 |
| `--for 초` 가 **재전송을 대신한다** | deadman 규약(8.1)을 스크립트 작성자가 직접 지키게 두면 반드시 잊는다. Ctrl-C로 끊어도 `finally`로 정지를 보낸다 — 멈추려고 누른 키가 오히려 700ms를 더 돌게 하면 안 된다 |
| `all`은 래퍼가 7번 부른다 (120ms 간격) | 게이트웨이에 브로드캐스트를 넣지 않는다. RS485 큐가 깊이 8이라(8.3절) 한꺼번에 밀면 뒤쪽이 버려진다. 실패한 카메라만 골라 보고할 수 있는 것도 이 구조 덕이다 |
| `all`과 `--for`는 **같이 못 쓴다** | 순차 실행이라 "7대가 동시에 움직인다"는 기대와 다르다. 그 오해가 예배 중에 드러나는 것보다 거절이 낫다 |
| `raw <action> [p1] [p2]` 탈출구 | 게이트웨이에 새 action이 생겨도 이 파일을 안 고치고 쓸 수 있다 |

## 5. 검토: Pelco-D를 UDP로 그대로 쏘기

처음 제안된 안이다. **틀린 발상은 아니다** — 게이트웨이가 이미 Pelco-D 파서를 갖고 있고,
IP 없는 슬롯은 받은 프레임을 그대로 `webTxEnqueue()`에 넣으면 되며, IP 슬롯에는 기존
번역 경로가 그대로 쓰인다. 구현은 40~60줄이다.

그럼에도 **1차 인터페이스로는 채택하지 않았다.**

| # | 문제 |
| --- | --- |
| 1 | **셸에서 못 친다.** 체크섬 붙은 7바이트를 손으로 만들어야 한다. cron이나 콘솔 매크로에 들어갈 줄이 아니고, 결국 호출자마다 인코더를 하나씩 갖게 된다 — 그 인코더는 표준 Pelco-D가 아니라 **우리 ED-P 방언**(AWB·BLC·셔터·게인은 EDIS SET 확장 프레임)이라 남의 라이브러리를 못 쓴다 |
| 2 | **응답할 자리가 없다.** "카메라 번호 범위 초과", "RS485 큐가 찼음", "이 버스는 Pelco-P라 마스터 송신을 못 함"을 돌려줄 방법이 없다. 쏘고 나면 됐는지 알 수 없다 |
| 3 | **접근 통제가 우회된다.** 제어 패널은 AP 접속에서 조작을 막는다(`controlAllowed()`). UDP 소켓을 열면 그 정책 밖에 문이 하나 더 생겨, 같은 판정을 손으로 다시 붙여야 한다(8.2절) |
| 4 | **deadman 규약을 모른다.** Pelco-D는 "컨트롤러가 계속 보낸다"를 전제한 프로토콜이다. 스크립트 작성자는 한 번만 쏘고, 카메라는 0.7초 뒤 멈춘다 |

**다시 볼 조건**: 바꿀 수 없는 기성 소프트웨어(조이스틱 앱, CCTV 소프트웨어 등)가 이미
Pelco-D를 뱉고 있고 그걸 붙여야 할 때. 그 경우엔 호환 수신구로서 값어치가 분명하다 —
다만 그건 *CLI*가 아니라 *호환 계층*이고, 필요해질 때 별도로 붙이면 된다.

## 6. 검토: 텍스트 한 줄 프로토콜 (보류)

Pelco-D UDP의 장점(가볍다, 한 방)은 살리고 단점(못 친다, 답이 없다)은 버리는 방법은
**바이트 대신 글자를 보내는 것**이다.

```sh
echo 'CAM6 MOVE 40 0'     | nc -u -w0 192.168.0.50 5290
echo 'CAM6 PRESET GOTO 3' | nc -u -w0 192.168.0.50 5290
```

- 한 줄 = 한 명령, 대소문자 무시. 낱말은 9절 어휘를 그대로 쓰고, 파서는 낱말을
  `(action, p1, p2)`로 바꿔 `webExecuteCommand()`를 부르는 **토크나이저에 불과하다**.
- 응답은 보낸 쪽 주소로 한 줄: `OK` 또는 `ERR <사유 문장>`. UDP라도 송신 포트로
  되돌려주면 되므로 5절의 2번 문제가 사라진다.
- **UDP와 TCP를 같은 포트에 함께 여는 것**을 권한다 (파서가 같아 비용이 거의 없다).
  UDP는 조이스틱·연속 이동용 — 재정렬돼도 마지막 값이 이기고 deadman이 받쳐준다.
  TCP는 프리셋 저장·모드 전환용 — **상태를 바꾸는 명령은 순서와 도착이 보장돼야 한다.**
  `PRESET SET`을 UDP로 보내면 유실·재정렬 시 엉뚱한 위치가 저장되고 아무도 모른다.
- 포트 번호는 **`config.h`의 컴파일 타임 상수**로 둔다. 설정 화면에 넣고 싶겠지만
  `SystemConfig`에 필드를 하나라도 추가하면 구조체 크기가 바뀌어 **저장된 Wi-Fi/카메라
  IP가 전부 초기화된다**(`doc/readme.md` 10.1절). 포트를 바꾸려고 현장 설정을 날릴 수는
  없다. 카메라가 쓰는 5678/52381과 겹치지 않으면 된다.

**넣을 조건**: 실제로 써 보고 HTTP 왕복이 느리다고 느껴질 때. 조이스틱을 붙이면 거의
확실히 필요해지고, 프리셋 자동화만 한다면 영영 필요 없다. 대략 150줄이다.

## 7. 폐기: VISCA over IP 수신

한때 "게이트웨이 내부 표준어가 VISCA이니 VISCA를 받으면 되지 않나"를 검토했으나
**폐기한다. 동작하지 않는다.**

이유는 라우팅에 있다. `RoutingTable::route()`는 받은 VISCA 패킷을 카메라 슬롯으로 보내되,
**`isConfigured()`(= IP가 비어 있지 않음)가 아닌 슬롯은 건너뛴다**
([RoutingTable.cpp:112](../src/RoutingTable.cpp#L112)). 그리고 게이트웨이에는
**VISCA → Pelco-D 번역기가 없다** — 있는 것은 반대 방향(버스의 Pelco-D를 IP 카메라용
VISCA로)뿐이다. 웹 제어가 RS485 카메라에 명령을 낼 때도 VISCA를 거치지 않고
`webSendPelco()`가 Pelco-D 프레임을 직접 만든다.

결과:

| 대상 | VISCA over IP로 들어온 명령 |
| --- | --- |
| IP가 설정된 슬롯(FoMaKo 등) | 전달된다 — 그런데 그건 **카메라에 직접 쏘면 되는 것**이라 게이트웨이를 거칠 이유가 없다 |
| IP가 없는 슬롯(ED-P, RS485) | **조용히 버려진다.** 카메라는 Pelco-D만 알아듣고, 번역해 줄 코드가 없다 |

즉 정작 게이트웨이가 필요한 쪽(RS485 카메라)에는 아무 효과가 없고, 효과가 있는 쪽은
게이트웨이가 필요 없다. 없는 번역기를 새로 만드는 것은 5절의 호환 계층보다 훨씬 큰
작업이고, 그렇게 얻는 것은 결국 9절 어휘와 같다.

## 8. 어떤 방식을 고르든 지켜야 하는 것

전송 방식보다 이쪽이 실제로 사고를 낸다.

### 8.1 연속 이동과 deadman — **가장 중요하다**

이동(`move`)·줌·포커스는 **누르고 있는 동안 움직이는** 명령이다. 게이트웨이는 명령을 받으면
`WEB_HOLD_TIMEOUT_MS`(현재 **700ms**) 동안만 유효한 hold를 걸고, 그 안에 다음 명령이 안 오면
**스스로 정지 명령을 낸다**(`pollWebDeadman()`). 브라우저 탭이 죽거나 Wi-Fi가 끊겨도
카메라가 계속 돌지 않게 하는 안전장치다.

호출자의 계약:

- 움직이는 동안 **300ms 간격으로 같은 명령을 반복**한다 (제어 패널이 하는 그대로).
- 멈출 때 **명시적으로 `stop`**을 보낸다. 안 보내도 0.7초 뒤 멈추지만 그만큼 더 간다.
- 한 번만 쏘면 "0.7초짜리 점프"가 된다. **각도를 재현하려면 이동이 아니라 프리셋을 쓴다.**

`ptz.py --for 초`가 이 세 가지를 대신한다 — 직접 HTTP를 부르는 코드를 짤 때는 직접 해야 한다.

### 8.2 누가 조작할 수 있나

지금 정책은 **"STA(평소 Wi-Fi) 접속 = 신뢰, AP 접속 = 모니터링만"** 하나뿐이고, 그 위에
비밀번호나 토큰은 없다(`doc/Web_controller.md` 1절). LAN에 붙은 것 자체가 신뢰 경계다.
`/api/cmd`도 같은 판정을 받으므로 **HTTP를 쓰는 한 이 정책이 자동으로 적용된다** — 새
포트를 열면 그때는 손으로 다시 붙여야 한다는 뜻이기도 하다(5절 3번).

토큰 인증은 넣지 않는다. 토큰을 저장하려면 `SystemConfig`를 넓혀야 하는데(6절), 그
대가(현장 설정 초기화)가 지금의 위험보다 크다.

### 8.3 얼마나 빨리 보내도 되나

RS485 경로에는 물리적 한계가 있다. 게이트웨이는 물리 컨트롤러(ZU-EPC7000)와 **같은 선**을
쓰므로, 자기 프레임을 밀어 넣기 전에 버스가 `WEB_TX_BUS_IDLE_MS`(30ms) 동안 조용해지기를
기다린다. 큐 깊이는 `WEB_TX_QUEUE_DEPTH`(**8**)이고, `WEB_TX_MAX_WAIT_MS`(500ms) 안에
자리를 못 잡으면 **버린다**.

- 버려진 개수는 설정 화면 Counters의 `Web RS485 TX Dropped`, `/api/state`의 `txDropped`,
  그리고 `ptz.py state` 마지막 줄에 보인다. **스크립트를 돌린 뒤 확인하는 습관을 들인다.**
- 실용적인 상한: RS485 카메라에 **초당 10회 안팎**. 그 이상은 물리 컨트롤러의 조작까지
  같이 씹히게 만든다.
- IP 카메라(6번 등)에는 이 제약이 없다.

### 8.4 주소

기본이 DHCP라 공유기를 재부팅하면 게이트웨이 IP가 바뀌고, 그러면 스크립트가 조용히
죽는다. **Static IP로 잡거나 공유기에서 MAC 예약**을 걸어 두는 것이 사실상 전제 조건이다
(Network Settings 또는 Serial 메뉴 `1 → 3 → 2`).

### 8.5 물리 컨트롤러와의 관계

**막을 방법이 없다.** ZU-EPC7000은 같은 선에 물려 있고 우리가 그 송신을 잠글 수단이 없다.
스크립트가 카메라를 움직이는 동안 사람이 조이스틱을 밀면 마지막 명령이 이긴다.

`/api/state`의 `busActive`(물리 컨트롤러가 최근 3초 안에 버스를 썼는가)로 **"지금 누가
만지고 있다"를 감지할 수는 있다** — `ptz.py state`의 `CTRL ACTIVE` 표시가 그것이다.
자동화 스크립트가 그때는 양보하도록 짜는 것이 예배 중 사고를 줄이는 현실적인 방법이다.
반대 방향(스크립트가 조작 중임을 컨트롤러에 알리기)은 불가능하다.

## 9. 명령 어휘 (전송 방식과 무관한 단일 출처)

`webExecuteCommand()`가 실제로 받는 것 전부다. 어떤 봉투를 쓰든 이 표를 따른다.

| action | p1 | p2 | `ptz.py` | 비고 |
| --- | --- | --- | --- | --- |
| `stop` | — | — | `stop` | Pan/Tilt·줌·포커스를 한꺼번에 멈춘다 |
| `move` | pan −63..63 (+우) | tilt −63..63 (+상) | `move <pan> <tilt>` | `0 0`은 `stop`과 같다. **연속**(8.1) |
| `zoom` | +1 tele / −1 wide / 0 정지 | 속도 0..7, 그 외는 기본속 | `zoom in\|out\|stop [속도]` | **연속.** RS485 경로에는 속도 개념이 없다 |
| `focus` | +1 far / −1 near / 0 정지 | — | `focus near\|far\|stop` | **연속** |
| `iris` | +1 open / −1 close | — | `iris open\|close` | 한 칸씩. AE가 MANUAL일 때만 효과 |
| `preset_goto` | 1..255 | — | `preset goto <n>` | |
| `preset_set` | 1..255 | — | `preset set <n>` | 순서 보장이 필요하다 (6절) |
| `preset_clear` | 1..255 | — | `preset clear <n>` | |
| `power` | **1 = ON**, 0 = STANDBY | — | `power on\|off` | |
| `ae` | **1 = MANUAL**, 0 = AUTO | — | `ae auto\|manual` | 컨트롤러 표기로는 IRIS AUTO/MANUAL |
| `focusmode` | **1 = MANUAL**, 0 = AUTO | — | `af auto\|manual` | |
| `awb` | **1 = MANUAL**, 0 = AUTO | — | `awb auto\|manual` | |
| `backlight` | **1 = ON**, 0 = OFF | — | `backlight on\|off` | |
| `onepush` | — | — | `onepush` | One Push AF. IP 경로는 2초 뒤 MANUAL로 되돌린다 |
| `rgain` `bgain` `shutter` `bright` | >0 증가, ≤0 감소 | — | `<이름> up\|down` | 한 칸씩. `bright`는 노출보정(ExpComp)이다 |

`cam`은 **1..7**이다(`CAMERA_SLOT_COUNT`).

> **`1`의 뜻이 항목마다 다르다.** `power 1`·`backlight 1`은 ON인데,
> `ae 1`·`awb 1`·`focusmode 1`은 **MANUAL**이다. 물리 컨트롤러의 키 배치를 그대로 옮긴
> 결과라 지금 바꾸면 화면과 어긋난다. 그래서 `ptz.py`는 숫자를 감추고 낱말만 받는다.

### 9.1 아직 없는 것

| | |
| --- | --- |
| **MENU** | 물리 컨트롤러의 MENU 키가 어떤 프레임을 내는지 아직 실측하지 못했다. 패널에서도 비활성이다 (`doc/Web_controller.md` 4절) |
| **절대 위치** | `move`는 속도 명령이다. 각도를 지정해서 가는 명령은 없다 — **프리셋으로 대신한다** |
| **Pelco-P 버스 마스터** | 입력이 Pelco-P인 버스에는 게이트웨이가 명령을 내지 못한다. 프레이밍과 주소 규칙이 달라 실측 없이 만들지 않았다. 그 상태에서 RS485 카메라를 부르면 오류 문장이 돌아온다 |

새 기능이 필요하면 **`webExecuteCommand()`에 action을 하나 추가하는 것**이 전부다. 제어
패널과 CLI가 동시에 그 기능을 얻는다 (`ptz.py`는 `raw`로 먼저 쓸 수 있고, 낱말은 나중에
붙이면 된다).

## 10. 다시 검토할 조건

- **HTTP 왕복이 느리다고 느껴지면** → 6절(텍스트 한 줄, UDP+TCP)을 넣는다.
- **Pelco-D밖에 못 뱉는 기성 도구를 붙여야 하면** → 5절을 호환 계층으로 붙인다.
- **VISCA over IP는 다시 보지 않는다** (7절).

어느 경우에도 명령 어휘는 9절 하나로 유지하고, 실행은 `webExecuteCommand()` 하나만
지나게 한다.
